# Architecture

Single-file web app: all HTML, CSS, and JavaScript live in `src/index.html`. No build step — `dist/index.html` is a manual copy/deploy artifact. `scripts/build.sh` (run in Git Bash) copies it to `dist/index.html`, stamping `const APP_VERSION = 'dev';` with `<short hash>[-dirty] <UTC date>` (logged at startup as `[webmetronome] version ...`), and zips it to `dist/webmetronome-<hash>.zip`.

Dependencies are CDN-only:
- Tailwind CSS (via CDN script tag)
- Google Fonts (Noto Sans KR)
- Web Audio API (browser built-in)

Open `src/index.html` directly in a browser — no server required.

## Audio Timing

The metronome uses the **Web Audio API lookahead scheduler** pattern for sample-accurate timing:

- `scheduler()` runs on `setTimeout(scheduler, lookahead)` (25ms intervals)
- It pre-schedules notes up to `scheduleAheadTime` (100ms) ahead using `audioCtx.currentTime`
- `nextNote()` advances `nextNoteTime` and `currentBeatIndex` based on the current subdivision
- `scheduleNote()` calls `playSound(time, toneType)` and `scheduleDraw()` — draw uses `setTimeout` offset from `audioCtx.currentTime` so visuals sync to audio
- **Never replace `audioCtx.currentTime`-based scheduling with `setInterval` or `Date.now()`**

## State Variables

All state is in module-level `let` vars (lines 539–579 of `src/index.html`):

| Group | Key vars |
|-------|----------|
| Playback | `isPlaying`, `bpm`, `subdivision`, `beatsPerMeasure`, `currentBeatIndex` |
| Audio | `audioCtx`, `masterGainNode`, `nextNoteTime`, `lookahead`, `scheduleAheadTime` |
| Timer | `isTimerActive`, `targetDuration`, `secondsRemaining`, `timerExpired` |
| Accel | `accelTargetBpm`, `accelStartBpm`, `accelTotalSeconds`, `accelMode`, `accelWeight`, `accelSchedule`, `accelMeasureCount` |
| Beat grid | `beatStates[]` — each element is 0 (normal), 1 (accent), 2 (strong accent), or 3 (mute) |

## Key Functions

- `togglePlay()` — starts/stops playback; captures accel anchor state on start, resets on stop
- `updateBpm(val)` — single entry point for all BPM changes (clamps to 30–250, updates slider + display)
- `buildAccelSchedule()` — precomputes the full BPM ramp schedule at play start
- `onMeasureEnd()` — called inside `nextNote()` at each measure boundary; steps BPM for accel
- `isAccelActive()` — guard used throughout accel logic
- `setTimer(minutes)` — activates/deactivates timer, syncs UI
- `initBeats()` / `renderBeatIndicators()` — rebuild the beat circle DOM when `beatsPerMeasure` changes
- `calcStepReps(startBpm, endBpm, effectiveSecs)` — computes per-BPM measure repetition counts for all three accel modes

## Tone Types

`playSound(time, toneType)`:
- `0` = normal beat (800 Hz)
- `1` = accent (600 Hz, softer)
- `2` = strong accent (1200 Hz, louder)
- `3` = mute (silent — `playSound` returns early)

Subdivisions on non-main beats always use tone type `0`.

## Accel Feature

BPM acceleration/deceleration ramps from `accelStartBpm` to `accelTargetBpm`. Three modes:
- `linear` — equal time per BPM step
- `count` — equal measure repetitions per BPM step
- `weighted` — front-loaded time distribution controlled by `accelWeight` slider

The schedule is precomputed into `accelSchedule[]` at play start (`buildAccelSchedule()`), indexed by measure count (`accelMeasureCount`). `onMeasureEnd()` looks up the next BPM from this array.

On stop: `accelStartBpm` is cleared (no BPM reset on stop — the ramp stays at wherever it ended). The "Off" button in the overlay clears `accelTargetBpm` entirely and turns off the timer.

For the design spec, see [specs/2026-03-18-bpm-acceleration-design.md](../superpowers/specs/2026-03-18-bpm-acceleration-design.md).

- **Clean-input auto tuning** (`OnsetCore.setAutoClean(true)`, on in the worklet, off by default so plain `new OnsetCore` and the Android golden are bit-identical): a clean line input (audio interface / DI) has a noise floor near -100 dBFS, and the fixed -55 dBFS absolute gate then muted the upper bands of a clean DI bass (only 54 % of 8th notes caught on a real capture). No raw-rise filter (it dropped legato notes). Mirrors the Android `DetectorTuning` (USB). The browser cannot see the device type, so it is chosen from the measured floor: `cleanBlock()` (once per 64-sample block, only on blocks that updated the floor) accumulates floor-update time; after >= 0.5 s (`CLEAN_WARM_SEC`, the floor starts at -100) the max band floor must stay < -80 dBFS (`CLEAN_NOISE_DB`) for 0.5 s of consecutive floor-update time (`CLEAN_HOLD_SEC`; short on purpose: a steady -75 dBFS noise floor rising from -100 is below -80 only from 0.5 s to about 0.7 s); then clean is LATCHED for the stream (never downgraded: the floor climbs to the sustain level while playing). The worklet posts `{type:'clean', clean:true, noiseDb}` once and adds `clean`/`noiseDb` to `level`. Page: `wm.timing.clean.<deviceId>` = '1' is sent as `config.cleanHint` once per stream (`timingAttachStream` -> `timingPostConfig(true)`; `setCleanHint` restarts the measurement and starts clean), so a known interface is clean at once. A hinted stream not measured clean after 60 s of floor-update time (`CLEAN_VERDICT_SEC`; long on purpose: floor-update time also accumulates between notes, so continuous playing reaches 10 s fast with a high sustain floor, and a pause of ~2.5 s is needed to measure) gets `{type:'clean', clean:false}`: the stored flag is removed for next time, the current stream keeps its tuning. The settings summary shows `Live 12 ms · S5 · Line` when clean; diagnostics include `cleanInput` and `noiseFloorDb`. Caveat: the floor only falls while the instrument is quiet, and the threshold is -80 dBFS (white noise latches below about -77 dBFS rms); without a hint, a real DI capture that is played continuously still latched only at a long pause (25 s). Replay of the real DI capture through the web core (tmp/di_replay.js): web S5 caught 53 of 119 slots, clean S5 88.
- **Quiet gate on onsets** (`OnsetCore.setQuietGateDb(db)`, config `quietDb`, off in a plain core, sent by the page on every stream attach and when `Quiet below` changes, for all inputs): the per-band gate had to drop to -90 dBFS on clean input, where an interface's own noise (~-83 dBFS) fires bursty onsets (122 in 20 s of synthetic +-6 dB noise; the user saw ~1000 hits at 75 BPM). A soft DI note's upper bands are far below -55, but its full-band raw peak (dominated by the fundamental) is far above -60, so an onset whose raw peak is below `Quiet below` (default -60 dBFS) is dropped. The raw peak is the per-block max of |x| from the trigger block through the 30 ms hold (`rbm`, updated in the existing per-sample loop; `qPk`). A dropped onset is undone: `onsetFrame` returns to its previous value (refractory and the 150 ms floor freeze do not see it, so noise cannot keep the floor at its -100 start) and the bands are re-armed (peak = current, dropped). Emitted onsets carry `rawDb`; the debug recorder gets `{type:'quietdrop', time, rawDb}`. Real DI capture (clean S5): 88 of 119 slots with or without the gate, slot onsets' raw peak min -27.5 / p5 -24.8 / median -21.3 dBFS (33 dB margin to -60), nothing dropped; the quietest second of the capture looped for 20 s gives 19 onsets without the gate and 0 with it.
- **Attack refinement** (`OnsetCore.setRefine(true)`, off in a plain core so the Android golden stays identical; the live worklet turns it on for all inputs). From a real E2x2 loopback capture of a sustained bass-like instrument (30 s, 160 BPM 8ths): onsets that include the top band (2.5-6 kHz) sit +1.3 ms (p90 3.3 ms) after the pick's HF burst, but low-band-only onsets were the problem. Three parts: (1) **backdate** - an onset with no top-band trigger looks back `REFINE_BACK_MS` (30) in the top band's block history (and the current block) for a spark (block max > the band's jump x max of the 8 blocks before it, above its gate) after the last top-band onset + refractory; if found the onset is reported there (`time` = spark block start, `backMs` = how far back; `onsetFrame` and the hold/refractory state are unchanged). Low-band-only triggers on the pick itself were 14-26 ms late. (2) **bloom guard** - without such a spark, a low-band-only onset within `REFINE_BLOOM_MS` (70) of a top-band onset is the note's body swelling (they came 40-66 ms, median 57, after the pick and, being louder, won the grid cell and replaced the pick, so the hit read ~55 ms late): no onset, bands re-armed not-dropped and `bloomHold` keeps following the swell's peak so its later blocks cannot pass the 1.5 x peak re-trigger; logged once as `{type:'quietdrop', reason:'bloom'}`. (3) **relative gate** - at the end of the hold an onset whose raw peak is 30 dB (`REFINE_REL`) below the median raw peak of the last 16 accepted onsets is dropped like a quiet drop (`reason:'relative'`): the capture's interface noise was bursty (silence: 50 ms raw peaks median -67, max -41 dBFS) so a noise-floor-relative gate could not separate it, but notes were -6..-14 dBFS. Capture result (cell winners scored against HF bursts found independently, zero-phase 1.5-10 kHz energy): winners on a strong attack 67 -> 72, low-band-only winners off any attack 25 -> 11, onsets in silence 5 -> 1, strong attacks caught 82 -> 85 of 101. The DI capture is unchanged (88/119). **Cell rule (page, `timingHandleOnset(time, peakDb, pick)`)**: pick = the onset's bands include the top band (the worklet sends `bands`; undefined = a pick, so synthetic test onsets behave as before). In one detect-grid cell a pick beats an onset without one either way round (the later, louder body of a note otherwise replaced its pick); between two of the same kind the loudest wins as before. Second capture (135 BPM, the swell came 56-130 ms after the pick with small HF ticks in between, beyond the 70 ms bloom window): low-band-only winners off any attack 26 -> 23 with the core alone, 16 with the cell rule; first capture 25 -> 6. A third capture recorded with the core refinement live (140 BPM): 22 -> 10, onsets in silence 4 -> 0. Remaining issues seen: noise before the player starts (string handling, -33..-57 dBFS raw) passes because the relative gate has no notes yet (Quiet below -40 removed 16 of 17 with no note lost on that setup); and about 16 of 75 strong HF bursts in the third capture, during sustained notes 50-250 ms after the previous onset, trigger nothing even without refine (the top band is probably not re-armed: it must fall below 0.7 x its peak or exceed 1.5 x it) - unverified, not changed. Quiet drops in the capture json carry `reason` (`quiet` / `relative` / `bloom`). `tools/replay-capture.js` replays with refine on; `--no-refine` for the old behaviour, `--dump file` writes the replayed onsets and drops as json.
- **Sensitivity** (1-10, default 5 = reference tuning, `wm.timing.sensitivity.<id>`, sent live in the worklet `config` message): `OnsetCore.setSensitivity(v)` scales every band jump (in dB), the combined-rise threshold and the gate (floor + 6 dB x f) by f (1.5 at 1, 1.0 at 5, 0.35 at 10), shifts the absolute gate (-55 dBFS + (5 - v) x 2 dB) and moves the re-trigger drop ratio (0.6 at 1, 0.7 at 5, 0.85 at 10). `params()` returns the effective values (also stored in the debug JSON).
- **Grid matching**: role-weighted capture. Each grid point scores |offset| / weight (beat 1.0, main off-beat 0.85, other 0.6); lowest wins; weight 0.5 for role 3 (finest, 32 grid); rejected as `ambiguous` if the runner-up is within 8 % or `too-far` if beyond the capture radius (0.42 x widest grid gap, clamped 0.16-0.45 beat, so a 16th hit on grid 8 is rejected). No fixed ms cap; views clamp at +/-50 ms, out-of-range hits draw as edge triangles (`.tm-tri`), rejected hits as grey crosses (`.tm-x`, status `Off grid`, not counted in the summary; vertical position = signed offset from the nearest slot, see below).
- **Input too hot**: the worklet level message carries the raw channel peak (`rawDb`) and a `clip` flag (true only for a run of >= `CLIP_RUN` = 4 consecutive instrument-channel samples with |x| >= `CLIP_LEVEL` = 0.998, tracked across quanta; a lone full-scale peak does not count; the ref channel never affects it); clip shows `#timingHot` (space reserved to avoid layout shift) and a red meter for 3 s.

Fields: `at`, `result`, `n/median/sd/mad/min/max/drift`, `ctxRate`, `baseLatencyMs`, `outputLatencyMs`, `trackRate/trackLatencyMs/channelCount/label`, `ctxTimeSec`, `pageAgeSec`, `streamAgeSec`, `streamSeq`, `pageLoadId`, `playedSinceLast`, `outTs`, `channel`, `sensitivity`. Reopening at START would pick a new random offset and invalidate the user's measurement, so START never reopens a stream. Instead `timingGlitchCompMs` (per stream) is the sum of `lengthMs` of real glitches since the later of: the stream attached, or the latency was last set (`timingSetLatency` = Apply or manual edit, or `timingResetLatency`); it is zeroed on `timingAttachStream` and on every latency set. `timingEffectiveLatencyMs()` (= `timingLatencyMs` + comp) is what `timingHandleOnset` subtracts (`tComp = onset - effective`) and what the settings button shows when comp > 0 (`Straight · 109 ms · S5`); the stored value is never changed. Loopback history records gain `zeroRuns`, `appliedMs` (stored latency), `compMs`, `expectedMs` (appliedMs + compMs, only when the latency source is a measurement on this same stream, i.e. same pageLoadId and streamSeq, else null) and `residualMs` (median - expectedMs, or null); the history line shows `zr N` when N > 0 and `Δ +0.1` when the residual is not null (verifies the compensation rule: it should be near 0). **Re-measure hint:** `timingSetLatency(ms, {streamSeq})` (Apply) stores `wm.timing.latencySrc.<id>` = `{pageLoadId, streamSeq}` (the stream the measurement finished on, captured in `timingLoop.seq`) and sets `timingMeasuredSeq`/`timingMeasuredPage`; a manual edit stores `{manual:true}` and clears them; Reset removes both keys. `timingNeedsRemeasure()` is true when `timingMeasuredSeq` is set and `pageLoadId` or `streamSeq` differ from the current ones (device switch, Timing off/on, reload); it shows an amber dot in `#timingSetBtn` and a `Re-measure` pill next to the LATENCY label (`timingRenderLatency`).

### Click ref channel (optional, default Off)
Why: every input stream gets a random ~80-90 ms offset and Chrome's input FIFO can slip by 10/20 ms, so a separate loopback measurement goes stale. When a device exposes the metronome on another channel of the SAME stream (e.g. an interface "Loopback" device: Ch 1 instrument, Ch 2 playback), that channel shares the instrument's timeline, and the click arrives there as a digital copy of our own, exactly known waveform (other audio, e.g. a backing track or YouTube, may be mixed into the same channel).
- **Template matching, not thresholds.** `RefTemplate` (worklet source, next to `OnsetCore`; factory `timingMakeRefTemplate(sr)` for tests) rebuilds each click from its parameters exactly as `playSound` makes it: a sine at 600/800/1200 Hz (tone 1/0/2), phase 0 at `osc.start(time)`, times a gain that steps to the start gain (1.5/1.8/3.0) at `time` and ramps exponentially to 0.001 over `dur = min(50 ms, 15% of the shortest interval)`. The loopback scale is irrelevant (NCC). The first 15 ms (or `dur`) of that waveform is the template. Measured through the real app (digital loopback with a whole-sample delay) the detected lag equals the delay to 0.0001 ms: the model of the oscillator and ramp is exact.
- **Scheduler hook.** `playSound` calls `timingRecordClick(time, freq, dur, gain)` for each audible click (only when `timingRefOn`; muted beats and their subdivisions record nothing; scheduling math untouched). It pushes the time into `timingClickTimes` (64, used for the lost warning and `timingRefState()`) and four numbers into `timingClickOut`; a microtask (`timingFlushClicks`, once per scheduler tick after it finished) posts `{type:'clicks', c:[sched, freq, dur, gain, ...]}` to the worklet. A tests/console call with only a time records the time but sends nothing.
- **Worklet (`RefTemplate`).** The ref channel goes through a 2nd-order high-pass 250 Hz and low-pass 2400 Hz (the template goes through the same filter, so the peak stays exactly at the true start) into a mirrored ring (>= 1.5 s, power of two). Clicks wait in a 256-entry queue; a click is searched once its whole window is in the ring, one at a time in order. Search = coarse sweep at stride `S` (~12 kHz, window energy slides), time-sliced to 150 k MACs per render quantum, then full rate +-`S` samples around up to 8 coarse peaks (one per click response, peaks >= 4 ms apart), then parabolic interpolation on the raw correlation (sub-sample). The peak is picked on the raw correlation (robust to loud bursts, which only inflate a normalizer) among candidates whose NCC (against the 15 ms template) is >= 0.6 (>= 0.65 for the first click of a run). Which response is this click's own: with a +-4 ms search the strongest; in the wider searches the one nearest the prediction among peaks >= 70% of the strongest (weaker ones are echoes of a click's decaying tail, which is the same waveform scaled); with no prediction the earliest (later clicks of the same tone follow it). Each search sweeps 4 ms beyond the accepted range so a carrier-cycle echo of a click just outside cannot win inside. Posts `{type:'ref', time: sched + lag, lagMs, ncc, sched}`; a miss posts nothing. Everything is preallocated (no allocation in `process()` except the event objects). Cost per 128-frame quantum measured in the browser: locked, 200 BPM 16ths in music, avg ~3-5 us and ~100 us in the quantum that finishes a click (budget 2.67 ms); the first-click 5-400 ms sweep spreads over ~8 quanta (worst 0.3-1 ms).
- **Lag ranges.** No prediction: 5-400 ms after the scheduled time. Prediction L: L +-4 ms; if that misses, L-5 ms .. L+45 ms (covers 10/20/40 ms input FIFO slips); a pure hint (below) then falls back to the whole 5-400 ms range. After each hit the worklet follows its own last lag until the main thread says otherwise.
- **Who tracks (main thread).** The main thread owns tracking because it already owns the median, the jump rule and `lost`; the worklet is a correlator. `timingPostTrack()` posts `{type:'track', lag, locked}` when it changes: `liveL` when locked, `liveL` as a mere hint (`locked:false`) when lost, the stored latency as a hint when Timing/the ref was switched on or changed mid-play (`timingRefHint`), and null at a play start. A worklet hint is what disambiguates same-tone clicks in a fast run when the stream changes mid-play; a null at a play start works because the first click has no predecessor.
- **Matching (pure).** Each ref event names its own click, so there is no pairing step: `timingRefMatch(state, sched, refTime)` locks on the first event, tracks `liveL = refTime - sched` as the median of the last 5 accepted offsets (gate 3 ms), holds an off-track offset as `pending` and adopts a jump after 2 events agreeing within 1 ms (logged as `ref-jump`), drops a lone outlier. `timingHandleRef(sched, time, ncc)` is the entry point (the worklet message handler and tests call it); `timingRefTick` flags lost after 1.5 s without an accepted event. Because pairing is explicit, the old restart guard (`timingRefIgnoreUntil`) and the "closest candidate" disambiguation are gone.
- `timingMatchLatencyMs()` is the single place `timingHandleOnset` gets L: `liveL + trim` when locked (no glitch compensation on top), otherwise `timingEffectiveLatencyMs()`. Settings: `wm.timing.refCh.<id>`, `wm.timing.refTrim.<id>`; `timingRefState()` for the console. With ref Off nothing changes (classic latency, Measure, glitch compensation, Re-measure hint).
- **Syncing (first lock).** In ref mode nothing is judged until the ref is confirmed: `timingRef.confirmed` becomes true when the click after the first lock agrees within 1 ms (a disagreeing one becomes the new first lock). Until then `timingHandleOnset` returns before matching (debug recorder reason `syncing`), nothing reaches Avg/Spread or the views, the status shows `Syncing…` (neutral, set by `timingRefTick`, cleared in `timingHandleRef` on confirm), and `#timingRefLive` shows `Live —` with an opacity-only pulse (`data-sync`, keyframes `tm-pulse`). A later `lost` keeps judging with the held liveL. Ref Off: unchanged.
- **Limits.** Per-event cycle slips: with a background as loud as the click (or louder) in the click's own band, noise can make a neighbouring carrier cycle (0.8-1.7 ms away) correlate best; at the same RMS none was seen in 120 simulated trials, at +6 dB about 8% of single events, which the median of 5 absorbs. Loud music with a strong partial at the click frequency can push the NCC under the gate (the click is then not reported; the lost warning covers a long run of misses). Same-tone clicks whose amplitudes differ by more than 30% (not produced by the app) are not told apart in the wide searches. A loud decaying noise burst can very rarely reach NCC 0.6 on its own. Spec: v1.3 and v1.4 sections.
- **View range** (`timingRangeMs`, 50 default / 100 / 200, persisted as `wm.timing.range`, `TIMING_RANGES`; popover item VIEW RANGE below DETECT, help key `range`): replaces the old fixed `TIMING_RANGE_MS`. Both views map ms to px through the one helper `timingRangeY(ms, half)` (`timingTlY` / `timingCY` just pass `TIMING_TL_HALF` / `TIMING_C_HALF`), and `timingMarkSetup(el, hit)` decides dot vs red edge triangle for the current range (quality thresholds stay in ms: `TIMING_GOOD_MS` = 10 is the band). `timingSetRange` -> `timingApplyRange` sets `--bh` (band height = true +/-10 ms in px), rebuilds the `.tm-rg` guide lines (`TIMING_RANGE_GUIDES`: 50 -> +/-25, 100 -> +/-25/50, 200 -> +/-50/100), updates the `.tm-scale` label (`+/-N ms`, under EARLY in both views) and re-places every existing marker immediately (Timeline items keep `it.hit`, On beats marks keep `el._hit`; no transition). Tests: `Timing Check - view range`.
- **One marker per grid cell** (main thread only, no worklet change): a cell is the region nearest one slot `(beatGlobal, pos)` of the current detect grid (slot +- half the gap to its neighbours), computed by `timingNearestCell()` (unweighted nearest slot, shares `timingBeatAt()` with `matchOnsetToGrid`). Every onset after latency compensation belongs to a cell, including ones the matcher turns into reject rings (`ambiguous`/`too-far`). Hits and rejects store the cell as `cbg`/`cpos` plus `peakDb`; `timingNearestCell()` also returns the slot time `t`, and a reject stores `offsetMs = (tComp - cell.t) * 1000`, drawn at `timingRejY()` (= `timingRangeY`, same sign as dots: early up, late down; beyond the view range it clamps to the edge line and stays a cross, no triangle). `timingApplyRange()` re-places crosses with the dots (`timingCPlaceRing` in On beats). `timingHandleOnset` calls `timingFindCellMark(cell)` (newest-first, stops once a beat older): an onset quieter than or equal to the cell's current marker is dropped (returns `null`, debug reason `merged`, no status change); a louder one removes the old marker (`timingRemoveCellMark`: `timingRemoveHitMark(hit)` for hits, `timingRemoveRingMark(rej)` for rings; timeline items carry `.hit`/`.rej`, On-beats elements `._hit`/`._rej`) and is then drawn as a hit or a ring per the matcher's verdict. Avg/Spread/count see one marker per cell. No global level filtering (a lone quiet sound is always shown); the meter flashes on every onset. A global quiet-hit FILTER setting and a time-window noise merge were tried and dropped.
- **Input channels (any count)**: `timingGetStream` asks for `channelCount: { ideal: 32 }` (Chrome picks the closest the device supports); the worklet node is `channelCount: 32, channelCountMode: 'max', channelInterpretation: 'discrete'`, so every input channel reaches `process` unmixed. `timingChannels` = `track.getSettings().channelCount` (1 if missing). The instrument selector (`#timingChSeg`, `timingRenderChSeg`) and the click-ref selector (`timingRenderRefSeg`: Off + every channel but the instrument) share one builder, `timingRenderChoice(host, opts, selected)`: up to `TIMING_SEG_MAX` (4) options render as segmented buttons, more as a compact `<select class="tm-select">` inside the host (`.tm-seg.tm-pick`). `timingWireChoice(host, onPick)` handles both the button click and the select change. Both hide when `timingChannels < 2`; persistence and mutual exclusion are unchanged. Tests: `Timing Check - many input channels`.
- **Help tips** (settings popover): one reusable component. `<button class="tm-help" data-help="key">` placeholders sit after each label (input, click, detect, latency, live, trim, sens, quiet); `TIMING_HELP` holds label + text, and at init each button gets `aria-label="Help: <label>"`, `aria-expanded`, `aria-controls` and a `role="tooltip"` bubble (`.tm-help-tip`, id `timingHelp-<key>`) appended to `#timingPopover`. Click/tap/Enter toggles, tapping the bubble dismisses it (no hover trigger); one open at a time (`timingHelpOpen`); closes on outside click (capture), Escape (capture, leaves the popover open) and when the popover closes. Bubbles fade with opacity only. To add a tip, add a placeholder button and a `TIMING_HELP` entry. Tests: `Timing Check - help tips`.

- **Timeline history, scroll and zoom**: history = `TIMING_HISTORY_BARS` (20) bars at the current meter/tempo, by time: `timingBeats` (time-pruned in `timingRecordBeat`, hard cap `TIMING_BEAT_CAP`), `timingHits`/`timingRejects` (pruned in `timingUpdateSummary`), practice waveform chunks (<= 90 s). All DOM items of the history exist (a few hundred, moved only by the track transform; `timingTlPrune` sweeps old ones every 500 ms), so per-frame work stays O(new items). View state: `timingTl.live` (follows NOW) / `timingTl.viewT` (context time under the anchor x while scrolled back); zoom = `timingTlBars()` (1..20 bars; portrait `timingTl.barsP`, persisted `wm.timing.tlbars`; practice `practice.bars`, `wm.practice.bars`, presets 2/4/8 lit only when equal). `timingTlRender(now)` is the only place that writes the track/NOW transforms (NOW slides off to the right while scrolled back; a `Now` pill (`#timingNowBtn`) returns to live). Gestures (`timingTlGestures`): pointer drag (after 5 px, horizontal only; CSS `touch-action: pan-y`), two-pointer pinch, Ctrl/Meta+wheel (trackpad pinch), horizontal/Shift+wheel, keys (arrows, Shift+arrows by bar, +/-, End). ## BPM detect (input tempo)

Optional helper inside Timing: the **BPM** button at the end of the meter row (`#bpmDetBtn`) opens `#bpmDetPanel` (detected tempo, `Steady beat` / `Unsteady — keep playing` / `Listening…` / `No steady beat`, `½` / `×2`, `Set`). Analysis only; the scheduler is never touched. Code: one `// BPM detect` block just before `// Practice mode`; state `bpmDet = { on, sent, env, step, lastT, mul, est, secs, timer }` sits next to `practice`.

- **Feed (worklet)**: `OnsetCore.setFlux(true)` (sent as `config.flux`, only once the detector was used, so the default config message is unchanged) makes the core build an onset-strength envelope from its 4 band maxima: per 256-sample frame, `sum over bands of max(0, log(1 + 1000 * frameMax) - max of the previous FLUX_LOOK (6) frames)`. The look-back max keeps the ripple of low notes from counting as attacks. Every 32 frames the processor posts `{type:'flux', time, step: 256/sr, v}` (time from the shared frame clock). `takeFlux()` is what tests use.
- **Grid floor**: the Detect grid is the shortest note the player plays, so `bpmDetTick` passes `stepsPerBeat = 1 / getTimingGrid().gap` (4 -> 1, 8 -> 2, 16 -> 4, triplet -> 3, 16 Shuffle -> 6) to `bpmEstimate`. The fastest steady pulse p (shortest-lag autocorrelation peak, local max, >= `BPM_DET_STEADY` and >= 0.6 of the highest peak, so weak spurious peaks and sparse/accented patterns never raise it) gives `minBpm = p / stepsPerBeat x 0.97`; candidates below it are skipped (a floor above `hi` is ignored). It only fixes "an octave too slow" (quarters at 200 with grid 4 -> 200, was 100); it cannot choose between 75 and 150 for 16ths. Absent `stepsPerBeat`, behaviour is unchanged. The grid is read on every tick, so changing it re-evaluates at once.
- **Estimate (main thread, pure)**: `bpmEstimate(env, fps)` -> `{ bpm, conf }` or null. Local mean (+-0.15 s) removed, smoothed +-10 ms (triangle) for the autocorrelation, candidates 40-240 BPM in 0.1 steps scored by the normalized autocorrelation at the period and its 2x/3x multiples (weights 1, 1/2, 1/3), times a log-Gaussian prior around 120 BPM (1 octave); parabolic refinement, then `bpmFitPulses(x, P)` fits a line through the peak nearest each expected pulse (outliers > 8 % of a period dropped, kept only within 3 % of P) for sub-0.2 BPM precision with human timing spread. `conf` = the score at the period; steady at >= `BPM_DET_STEADY` (0.2).
- **Loop**: `bpmDetIn` keeps the last ~8 s (`BPM_DET_WIN`; a time gap restarts it); `bpmDetTick` runs every 500 ms (`setInterval`, only while on) after `BPM_DET_MIN` (3 s). Octave errors (a fast tempo read as its half) are left to the user via `½` / `×2` (`bpmDet.mul`). `Set` = `updateBpm(round)` + `resetAccelAnchor()`.
- **Off**: toggling the button, `timingStop()`, entering Practice mode (the button is hidden there).
- **Tests**: `tests/bpm.spec.js` (synthetic audio through `OnsetCore` -> `bpmEstimate`; UI).

## Capture export (detector analysis)

Timing settings popover, last section **Capture**: `Save last take` (`#timingCaptureBtn`; enabled while a take has data and the stream exists) downloads `capture-<YYYYMMDD-HHMMSS>.wav / .csv / .json` (+ `-click.wav` with a click channel). Meant for improving the detector offline: the data of the current or last take. Code: one `// Capture export` block just before the debug recorder; worklet ring in `TIMING_WORKLET_SRC`. The scheduler is not involved (the only hook is one `timingCapPush` in `timingRecordClick`).

- **Take model** (arm/disarm): the worklet records ONLY while armed. `timingResetSession` (play start via `timingOnPlayStart`, and Timing switched on mid-play in `timingStart`) calls `timingCapBegin()`: clears the page log and posts `{type:'config', capture:'arm', id}`; the worklet clears its rings and records (a new take replaces the old one). Stop (`timingOnPlayStop`) -> `timingCapStop()` posts `{capture:'stop', afterSec: 1.5}`; the worklet counts 1.5 s of frames itself (exact to the frame, the last quantum is cut), disarms and posts `{type:'capend', id, frame}`. After that the ring and the page log are frozen until the next Start, so saving long after Stop still gives the take (last 30 s of it, incl. the 1.5 s tail; shorter takes export whole). A `capend` of an older take (`id` mismatch) is ignored. Saved during a take = the last 30 s up to now. Stream attach (`cleanHint`) or a channel change while armed restarts the ring mid-take (log is reset on attach, beats kept); a frozen take ignores channel changes, a stream attach wipes it (button disabled until the next Start). Timing off drops everything.
- **Worklet rings**: `OnsetDetector` keeps the last `TIMING_CAP_SEC` (30) s of the analysed channel in a preallocated `Float32Array(sampleRate * 30)` (96 kHz -> 11.5 MB, 48 kHz -> 5.8 MB). One `set()` copy per render quantum (`capWrite`), no per-sample JS. The click-loopback ring `ccap` (same size) is allocated lazily the first time a ref channel is configured (96 kHz with a ref: 23 MB total; without: unchanged) and written in lockstep (same write position; zeros while the ref channel is unavailable), so both always share the start frame and length. A real gap in the frame clock is filled with silence. `config.dump = true` -> `{type:'capture', frame, sr, samples, click (null unless a ref channel was used in the take), refCh, armed, id}` (buffers transferred; `frame` = input frame of the first sample). Quiet-gate drops (`quietdrop`) are always reported.
- **Page log** (`timingCap`, pruned to ~33 s by entry time while recording, hard cap 6000 each; NOT pruned once frozen): `beats` (from `timingRecordBeat`), `clicks` (scheduled audible click times, only with a ref channel), `onsets` (one record per onset message: `time, peakDb, rawDb, thDb, bands, latMs` = latency used for matching at receipt, plus the verdict from `timingLogMatch`: `hit` with `offsetMs/pos/role/beatInMeasure`, or a reject reason `ambiguous | too-far | merged | not-playing | syncing | before-first-beat | measuring | muted`, or `replaced` when a louder sound took the same cell), `events` (ref results/lock/lag, clean state changes), `drops` (quiet-gate drops). Once `capend` arrives (`timingCapEnd`, seconds) entries with a later time are dropped. `timingDbgMatch` became `timingLogMatch`, shared with the debug recorder.
- **Clock convention** (same meaning as the Android app): everything is in **context frames** (audio-context time x sampleRate). `beat,<frame>,<beatInMeasure>` = time the click is scheduled to sound (Android: output frame). `onset,<frame>,<peakDb>,<verdict>` = the raw detector time in input frames, before latency compensation. `latencyFrames` = the latency used for matching (`timingMatchLatencyMs()`, at export time); an onset belongs to a beat/slot at `beat + latencyFrames`. `wavStartInFrame` = frame of the wav's first sample. Difference to Android: web input and output share one clock (the context), Android's are separate counters tied by the loopback offset; the arithmetic is identical.
- **CSV**: exactly one `#` header line (analysis scripts split it into `key=value`, so no values with spaces or `=`): `# sampleRate= latencyFrames= wavStartInFrame= bpm= beats=<per measure> rhythm=<subdivision> grid=<detect grid key> sensitivity= detector=web-onsetcore platform=web clock=ctx-frames app=<APP_VERSION> latencyMs= clean=0|1 noiseDb= quietDb= channel=<1-based> device=<label> ua=<Browser/major>`, then `beat,<frame>,<beatInMeasure>` (from 2 s before the wav start) and `onset,<frame>,<peakDb>,<verdict>` lines (only inside the wav range). With a click channel the header ends with ` clickWav=1 refChannel=<1-based>` (absent otherwise). Verdict as Android: `hit +5.02 ms pos=0.500`, `reject ambiguous +3.0 ms`, or a bare reason.
- **JSON**: `format: 'webmetronome-capture'`, `clock` text, `meta` (= `timingMetaSnapshot()`: settings, `detector` = `timingMakeOnsetCoreParams` with the live clean/quiet values, `trackSettings`, device label, user agent, latency parts, ref state), `wav` (+ `clickWav`, `refChannel`, `takeOpen` = saved during a take), `beats`, `clicks` (`{frame,time}` scheduled click times), `onsets` (all fields + `frame` + `verdictText`), `quietDrops`, `events` (ref lock/lag events included).
- **Click wav**: `capture-<stamp>-click.wav` = mono float32, same sampleRate, start frame (`wavStartInFrame`) and length as the instrument wav, the loopback of the metronome click. `capture-<stamp>.wav` stays the mono instrument stream (Android scripts read it as one float stream).
- **Replay tool**: `node tools/replay-capture.js <capture> [--sens N] [--gate dB] [--clean|--no-clean|--auto] [--quiet dB] [--window ms] [--slots N] [--no-refine] [--dump file] [--list] [--diff]`. Loads `OnsetCore` from `src/index.html` (like the Android `tools/gen_onset_golden.js`), re-runs it over the wav (128-sample blocks, like the worklet) and prints the onset count, a score against the grid slots implied by the beats (`hit n/N slots`, extras, dups, offset median/mean/SD) and a diff against the onsets recorded in the csv. Defaults come from the csv header (sensitivity, `clean=`, `quietDb=`); `--auto` mimics the live worklet's clean auto-detection. If `<capture>-click.wav` exists it adds an accuracy section: each scheduled click (json `clicks`, else csv beats) is located in the click wav from its peak back to the rising edge (earliest sample >= 15 % of the peak with no gap > 0.5 ms; the loopback channel can carry the instrument too, so the first loud sample is not the click); reports the measured loopback latency (median, SD, min/max, drift in ms/min) vs `latencyFrames` (= the latency error that shifted every hit) and the recorded hit offsets recomputed with the median and the nearest-click latency. Works on Android captures too. Android DI capture `capture-20261031-182037`: plain web tuning 53/119 slots, `--clean` 88/119, and the plain replay reproduces the csv's 54 recorded onsets exactly.
- **Tests**: `tests/capture.spec.js` (ring contents/gap/channel change, arm/tail/freeze, lazy click ring, button state, log pruning and freeze, export after Stop, click wav/keys, wav/csv/json of a live flow, replay tool on the saved files, replay accuracy section on a synthetic capture with a 3 ms latency error).
