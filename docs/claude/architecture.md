# Architecture

Single-file web app: all HTML, CSS, and JavaScript live in `src/index.html`. No build step — `dist/index.html` is a manual copy/deploy artifact.

Dependencies are CDN-only:
- Tailwind CSS (via CDN script tag)
- Google Fonts (Noto Sans KR)
- Web Audio API (browser built-in)

Open `src/index.html` directly in a browser — no server required.

## Audio Timing

The metronome uses the **Web Audio API lookahead scheduler** pattern for sample-accurate timing:

- `scheduler()` runs on `setTimeout(scheduler, lookahead)` (25ms intervals)
- It pre-schedules notes up to `scheduleAheadTime` (100ms) ahead using `audioCtx.currentTime`
- `nextNote()` advances `nextNoteTime` and `currentBeatIndex` based on the current subdivision
- `scheduleNote()` calls `playSound(time, toneType)` and `scheduleDraw()` — draw uses `setTimeout` offset from `audioCtx.currentTime` so visuals sync to audio
- **Never replace `audioCtx.currentTime`-based scheduling with `setInterval` or `Date.now()`**

## State Variables

All state is in module-level `let` vars (lines 539–579 of `src/index.html`):

| Group | Key vars |
|-------|----------|
| Playback | `isPlaying`, `bpm`, `subdivision`, `beatsPerMeasure`, `currentBeatIndex` |
| Audio | `audioCtx`, `masterGainNode`, `nextNoteTime`, `lookahead`, `scheduleAheadTime` |
| Timer | `isTimerActive`, `targetDuration`, `secondsRemaining`, `timerExpired` |
| Accel | `accelTargetBpm`, `accelStartBpm`, `accelTotalSeconds`, `accelMode`, `accelWeight`, `accelSchedule`, `accelMeasureCount` |
| Beat grid | `beatStates[]` — each element is 0 (normal), 1 (accent), 2 (strong accent), or 3 (mute) |

## Key Functions

- `togglePlay()` — starts/stops playback; captures accel anchor state on start, resets on stop
- `updateBpm(val)` — single entry point for all BPM changes (clamps to 30–250, updates slider + display)
- `buildAccelSchedule()` — precomputes the full BPM ramp schedule at play start
- `onMeasureEnd()` — called inside `nextNote()` at each measure boundary; steps BPM for accel
- `isAccelActive()` — guard used throughout accel logic
- `setTimer(minutes)` — activates/deactivates timer, syncs UI
- `initBeats()` / `renderBeatIndicators()` — rebuild the beat circle DOM when `beatsPerMeasure` changes
- `calcStepReps(startBpm, endBpm, effectiveSecs)` — computes per-BPM measure repetition counts for all three accel modes

## Tone Types

`playSound(time, toneType)`:
- `0` = normal beat (800 Hz)
- `1` = accent (600 Hz, softer)
- `2` = strong accent (1200 Hz, louder)
- `3` = mute (silent — `playSound` returns early)

Subdivisions on non-main beats always use tone type `0`.

## Accel Feature

BPM acceleration/deceleration ramps from `accelStartBpm` to `accelTargetBpm`. Three modes:
- `linear` — equal time per BPM step
- `count` — equal measure repetitions per BPM step
- `weighted` — front-loaded time distribution controlled by `accelWeight` slider

The schedule is precomputed into `accelSchedule[]` at play start (`buildAccelSchedule()`), indexed by measure count (`accelMeasureCount`). `onMeasureEnd()` looks up the next BPM from this array.

On stop: `accelStartBpm` is cleared (no BPM reset on stop — the ramp stays at wherever it ended). The "Off" button in the overlay clears `accelTargetBpm` entirely and turns off the timer.

For the design spec, see [specs/2026-03-18-bpm-acceleration-design.md](../superpowers/specs/2026-03-18-bpm-acceleration-design.md).

Design: [specs/2026-10-23-timing-check-design.md](../superpowers/specs/2026-10-23-timing-check-design.md), plan: [plans/2026-10-23-timing-check.md](../superpowers/plans/2026-10-23-timing-check.md). Worklet posts `level` (every 1024 frames) and `onset` (after a 30 ms hold). `timingOnWorkletMessage()` routes them. Devices: `timingRefreshDevices()`, `timingSwitchDevice()`, `devicechange` listener.

LATENCY row (-/value/+, hold-to-repeat, click-to-type, Reset) via `timingWireStepper()`/`timingSetLatency()`; saved per device (`wm.timing.latency.<id>`); without a saved value `timingEstimateLatencyMs()` (outputLatency + baseLatency + track latency) is used and `est.` is shown. Synthetic scenarios live in `tests/helpers/scenarios.js`.

- **Tests**: `tests/timing.spec.js`; `playwright.config.js` launches Chromium with `--use-fake-ui-for-media-stream --use-fake-device-for-media-stream`.
- **Debug recorder** (developer only, console): `timingDebugRecord(seconds = 20)` / `timingDebugStop()`. While recording, the worklet streams raw samples of the selected channel (1024-sample chunks with their context frame) and posts near-miss events; the page logs beats, onsets (with triggering bands and rise), match results (accepted or rejected with reason) and, at the end, downloads `timing-debug-<timestamp>.wav` (32-bit float mono) and `.json` and prints a summary. Nothing runs unless recording.
- **Sensitivity** (1-10, default 5 = reference tuning, `wm.timing.sensitivity.<id>`, sent live in the worklet `config` message): `OnsetCore.setSensitivity(v)` scales every band jump (in dB), the combined-rise threshold and the gate (floor + 6 dB x f) by f (1.5 at 1, 1.0 at 5, 0.35 at 10), shifts the absolute gate (-55 dBFS + (5 - v) x 2 dB) and moves the re-trigger drop ratio (0.6 at 1, 0.7 at 5, 0.85 at 10). `params()` returns the effective values (also stored in the debug JSON).
- **Grid matching**: role-weighted capture. Each grid point scores |offset| / weight (beat 1.0, main off-beat 0.85, other 0.6); lowest wins; weight 0.5 for role 3 (finest, 32 grid); rejected as `ambiguous` if the runner-up is within 8 % or `too-far` if beyond the capture radius (0.42 x widest grid gap, clamped 0.16-0.45 beat, so a 16th hit on grid 8 is rejected). No fixed ms cap; views clamp at +/-50 ms, out-of-range hits draw as edge triangles (`.tm-tri`), rejected hits as grey crosses (`.tm-x`, status `Off grid`, not counted in the summary; vertical position = signed offset from the nearest slot, see below).
- **Input too hot**: the worklet level message carries the raw channel peak (`rawDb`) and a `clip` flag (true only for a run of >= `CLIP_RUN` = 4 consecutive instrument-channel samples with |x| >= `CLIP_LEVEL` = 0.998, tracked across quanta; a lone full-scale peak does not count; the ref channel never affects it); clip shows `#timingHot` (space reserved to avoid layout shift) and a red meter for 3 s.
- **Loopback measurement** (optional, `Measure` in the LATENCY row): `timingLoopStart()` schedules 60 clicks 0.5 s apart from a dedicated synth (1.2 kHz, 5 ms, own GainNode, independent of app volume/mute); onsets are routed to `timingLoopOnset()` (first onset in [ts, ts+0.4) per click) and never reach the matcher/views. `timingLoopFinish()` computes median/SD/MAD/range/drift/misses; success (>= 40 samples, MAD, SD <= 2 ms, |drift| <= 1 ms/min) offers `Apply`; result saved as `wm.timing.loopback.<id>` and shown in the LATENCY tooltip. START cancels (`timingLoopCancel`).
- **Measurement history** (diagnostics): every finished measurement (good/unstable/failed, not cancelled) appends a record to `wm.timing.loopHistory.<id>` (last 30; `timingLoopHistory()` returns it). Fields: `at`, `result`, `n/median/sd/mad/min/max/drift`, `ctxRate`, `baseLatencyMs`, `outputLatencyMs`, `trackRate/trackLatencyMs/channelCount/label`, `ctxTimeSec`, `pageAgeSec`, `streamAgeSec`, `streamSeq`, `pageLoadId`, `playedSinceLast`, `outTs`, `channel`, `sensitivity`. Shown (newest 10) in the Measure panel's History details with Copy JSON / Clear; rows are tinted when ctx and input sample rates differ, and marked when the stream or page load changed.
- **Input glitches are compensated, never reopened; a measurement is valid only for its stream** (reason: each time Chrome opens an input stream the round-trip offset is set at random within ~80-90 ms and stays fixed for that stream, except that Chrome sometimes underruns the input FIFO, inserts exact-zero samples, and the round-trip latency then grows permanently by exactly the run length; measured on real hardware: a 10 ms render buffer gave +10.00 ms per glitch, latencyHint 0.02 gave runs of exactly 960 samples = 20 ms). Reopening at START would pick a new random offset and invalidate the user's measurement, so START never reopens a stream. Instead `timingGlitchCompMs` (per stream) is the sum of `lengthMs` of real glitches since the later of: the stream attached, or the latency was last set (`timingSetLatency` = Apply or manual edit, or `timingResetLatency`); it is zeroed on `timingAttachStream` and on every latency set. `timingEffectiveLatencyMs()` (= `timingLatencyMs` + comp) is what `timingHandleOnset` subtracts (`tComp = onset - effective`) and what the settings button shows when comp > 0 (`Straight · 109 ms · S5`); the stored value is never changed. The LATENCY row shows `+20 ms auto (1 glitch)` (`#timingLatComp`, tooltip `Chrome's input buffer slipped; the extra delay is added automatically.`) and, while playing, the status becomes `Input glitch — compensated +20 ms` (warn, 4 s). **Startup ignore window:** a brand-new stream reports a ~20 ms zero run ~0.04 s after attaching that is not a real glitch, so a run whose `startTime` is within 1.0 s (`TIMING_STARTUP_IGNORE_SEC`) of `timingStreamCtxAt` (`audioCtx.currentTime` at attach, compared in context time) is logged with `ignored:'startup'` and does not count toward `timingGlitchCount`/`timingGlitchMsTotal`/compensation and shows no warning; the quantum-based `timingOnZeroRuns` path (running `zeroRuns` count on `level` messages, count only) applies the same window. `timingAttachStream()` connects the new source to the existing worklet node, disconnects the old source and only then stops the old tracks (device switch, Timing off/on). `timingSwapUntil` suppresses No input / Quiet for 1.5 s after any attach. `OnsetCore.scanZero()` counts render quanta that are exactly all 0.0 after non-zero data (once per run, selected raw channel). Loopback history records gain `zeroRuns`, `appliedMs` (stored latency), `compMs`, `expectedMs` (appliedMs + compMs, only when the latency source is a measurement on this same stream, i.e. same pageLoadId and streamSeq, else null) and `residualMs` (median - expectedMs, or null); the history line shows `zr N` when N > 0 and `Δ +0.1` when the residual is not null (verifies the compensation rule: it should be near 0). **Re-measure hint:** `timingSetLatency(ms, {streamSeq})` (Apply) stores `wm.timing.latencySrc.<id>` = `{pageLoadId, streamSeq}` (the stream the measurement finished on, captured in `timingLoop.seq`) and sets `timingMeasuredSeq`/`timingMeasuredPage`; a manual edit stores `{manual:true}` and clears them; Reset removes both keys. `timingNeedsRemeasure()` is true when `timingMeasuredSeq` is set and `pageLoadId` or `streamSeq` differ from the current ones (device switch, Timing off/on, reload); it shows an amber dot in `#timingSetBtn` and a `Re-measure` pill next to the LATENCY label (`timingRenderLatency`).

### Click ref channel (optional, default Off)
Why: every input stream gets a random ~80-90 ms offset and Chrome's input FIFO can slip by 10/20 ms, so a separate loopback measurement goes stale. When a device exposes the metronome on another channel of the SAME stream (e.g. an interface "Loopback" device: Ch 1 instrument, Ch 2 playback), that channel shares the instrument's timeline, and the click arrives there as a digital copy of our own, exactly known waveform (other audio, e.g. a backing track or YouTube, may be mixed into the same channel).
- **Template matching, not thresholds.** `RefTemplate` (worklet source, next to `OnsetCore`; factory `timingMakeRefTemplate(sr)` for tests) rebuilds each click from its parameters exactly as `playSound` makes it: a sine at 600/800/1200 Hz (tone 1/0/2), phase 0 at `osc.start(time)`, times a gain that steps to the start gain (1.5/1.8/3.0) at `time` and ramps exponentially to 0.001 over `dur = min(50 ms, 15% of the shortest interval)`. The loopback scale is irrelevant (NCC). The first 15 ms (or `dur`) of that waveform is the template. Measured through the real app (digital loopback with a whole-sample delay) the detected lag equals the delay to 0.0001 ms: the model of the oscillator and ramp is exact.
- **Scheduler hook.** `playSound` calls `timingRecordClick(time, freq, dur, gain)` for each audible click (only when `timingRefOn`; muted beats and their subdivisions record nothing; scheduling math untouched). It pushes the time into `timingClickTimes` (64, used for the lost warning and `timingRefState()`) and four numbers into `timingClickOut`; a microtask (`timingFlushClicks`, once per scheduler tick after it finished) posts `{type:'clicks', c:[sched, freq, dur, gain, ...]}` to the worklet. A tests/console call with only a time records the time but sends nothing.
- **Worklet (`RefTemplate`).** The ref channel goes through a 2nd-order high-pass 250 Hz and low-pass 2400 Hz (the template goes through the same filter, so the peak stays exactly at the true start) into a mirrored ring (>= 1.5 s, power of two). Clicks wait in a 256-entry queue; a click is searched once its whole window is in the ring, one at a time in order. Search = coarse sweep at stride `S` (~12 kHz, window energy slides), time-sliced to 150 k MACs per render quantum, then full rate +-`S` samples around up to 8 coarse peaks (one per click response, peaks >= 4 ms apart), then parabolic interpolation on the raw correlation (sub-sample). The peak is picked on the raw correlation (robust to loud bursts, which only inflate a normalizer) among candidates whose NCC (against the 15 ms template) is >= 0.6 (>= 0.65 for the first click of a run). Which response is this click's own: with a +-4 ms search the strongest; in the wider searches the one nearest the prediction among peaks >= 70% of the strongest (weaker ones are echoes of a click's decaying tail, which is the same waveform scaled); with no prediction the earliest (later clicks of the same tone follow it). Each search sweeps 4 ms beyond the accepted range so a carrier-cycle echo of a click just outside cannot win inside. Posts `{type:'ref', time: sched + lag, lagMs, ncc, sched}`; a miss posts nothing. Everything is preallocated (no allocation in `process()` except the event objects). Cost per 128-frame quantum measured in the browser: locked, 200 BPM 16ths in music, avg ~3-5 us and ~100 us in the quantum that finishes a click (budget 2.67 ms); the first-click 5-400 ms sweep spreads over ~8 quanta (worst 0.3-1 ms).
- **Lag ranges.** No prediction: 5-400 ms after the scheduled time. Prediction L: L +-4 ms; if that misses, L-5 ms .. L+45 ms (covers 10/20/40 ms input FIFO slips); a pure hint (below) then falls back to the whole 5-400 ms range. After each hit the worklet follows its own last lag until the main thread says otherwise.
- **Who tracks (main thread).** The main thread owns tracking because it already owns the median, the jump rule and `lost`; the worklet is a correlator. `timingPostTrack()` posts `{type:'track', lag, locked}` when it changes: `liveL` when locked, `liveL` as a mere hint (`locked:false`) when lost, the stored latency as a hint when Timing/the ref was switched on or changed mid-play (`timingRefHint`), and null at a play start. A worklet hint is what disambiguates same-tone clicks in a fast run when the stream changes mid-play; a null at a play start works because the first click has no predecessor.
- **Matching (pure).** Each ref event names its own click, so there is no pairing step: `timingRefMatch(state, sched, refTime)` locks on the first event, tracks `liveL = refTime - sched` as the median of the last 5 accepted offsets (gate 3 ms), holds an off-track offset as `pending` and adopts a jump after 2 events agreeing within 1 ms (logged as `ref-jump`), drops a lone outlier. `timingHandleRef(sched, time, ncc)` is the entry point (the worklet message handler and tests call it); `timingRefTick` flags lost after 1.5 s without an accepted event. Because pairing is explicit, the old restart guard (`timingRefIgnoreUntil`) and the "closest candidate" disambiguation are gone.
- `timingMatchLatencyMs()` is the single place `timingHandleOnset` gets L: `liveL + trim` when locked (no glitch compensation on top), otherwise `timingEffectiveLatencyMs()`. Settings: `wm.timing.refCh.<id>`, `wm.timing.refTrim.<id>`; `timingRefState()` for the console. With ref Off nothing changes (classic latency, Measure, glitch compensation, Re-measure hint).
- **Syncing (first lock).** In ref mode nothing is judged until the ref is confirmed: `timingRef.confirmed` becomes true when the click after the first lock agrees within 1 ms (a disagreeing one becomes the new first lock). Until then `timingHandleOnset` returns before matching (debug recorder reason `syncing`), nothing reaches Avg/Spread or the views, the status shows `Syncing…` (neutral, set by `timingRefTick`, cleared in `timingHandleRef` on confirm), and `#timingRefLive` shows `Live —` with an opacity-only pulse (`data-sync`, keyframes `tm-pulse`). A later `lost` keeps judging with the held liveL. Ref Off: unchanged.
- **Limits.** Per-event cycle slips: with a background as loud as the click (or louder) in the click's own band, noise can make a neighbouring carrier cycle (0.8-1.7 ms away) correlate best; at the same RMS none was seen in 120 simulated trials, at +6 dB about 8% of single events, which the median of 5 absorbs. Loud music with a strong partial at the click frequency can push the NCC under the gate (the click is then not reported; the lost warning covers a long run of misses). Same-tone clicks whose amplitudes differ by more than 30% (not produced by the app) are not told apart in the wide searches. A loud decaying noise burst can very rarely reach NCC 0.6 on its own. Spec: v1.3 and v1.4 sections.
- **View range** (`timingRangeMs`, 50 default / 100 / 200, persisted as `wm.timing.range`, `TIMING_RANGES`; popover item VIEW RANGE below DETECT, help key `range`): replaces the old fixed `TIMING_RANGE_MS`. Both views map ms to px through the one helper `timingRangeY(ms, half)` (`timingTlY` / `timingCY` just pass `TIMING_TL_HALF` / `TIMING_C_HALF`), and `timingMarkSetup(el, hit)` decides dot vs red edge triangle for the current range (quality thresholds stay in ms: `TIMING_GOOD_MS` = 10 is the band). `timingSetRange` -> `timingApplyRange` sets `--bh` (band height = true +/-10 ms in px), rebuilds the `.tm-rg` guide lines (`TIMING_RANGE_GUIDES`: 50 -> +/-25, 100 -> +/-25/50, 200 -> +/-50/100), updates the `.tm-scale` label (`+/-N ms`, under EARLY in both views) and re-places every existing marker immediately (Timeline items keep `it.hit`, On beats marks keep `el._hit`; no transition). Tests: `Timing Check - view range`.
- **One marker per grid cell** (main thread only, no worklet change): a cell is the region nearest one slot `(beatGlobal, pos)` of the current detect grid (slot +- half the gap to its neighbours), computed by `timingNearestCell()` (unweighted nearest slot, shares `timingBeatAt()` with `matchOnsetToGrid`). Every onset after latency compensation belongs to a cell, including ones the matcher turns into reject rings (`ambiguous`/`too-far`). Hits and rejects store the cell as `cbg`/`cpos` plus `peakDb`; `timingNearestCell()` also returns the slot time `t`, and a reject stores `offsetMs = (tComp - cell.t) * 1000`, drawn at `timingRejY()` (= `timingRangeY`, same sign as dots: early up, late down; beyond the view range it clamps to the edge line and stays a cross, no triangle). `timingApplyRange()` re-places crosses with the dots (`timingCPlaceRing` in On beats). `timingHandleOnset` calls `timingFindCellMark(cell)` (newest-first, stops once a beat older): an onset quieter than or equal to the cell's current marker is dropped (returns `null`, debug reason `merged`, no status change); a louder one removes the old marker (`timingRemoveCellMark`: `timingRemoveHitMark(hit)` for hits, `timingRemoveRingMark(rej)` for rings; timeline items carry `.hit`/`.rej`, On-beats elements `._hit`/`._rej`) and is then drawn as a hit or a ring per the matcher's verdict.
